# P2-03. Однонаправленный канал: запрещает компилятор, а машинный код тот же

**Спросили (26:39):** «Есть же еще однонаправленные каналы, только чтение или только запись. Зачем
такая штука нужна?»

**Сказано (27:10):** «Когда мы создаем канал, он в любом случае многонаправленный (двунаправленный).
Но дальше мы можем его передать в какую-нибудь горутину, которая может в него только читать или
только писать.»

**Сказано (28:14):** «Давайте попробуем в этот канал записать. Запретит ли нам в него писать
runtime? Да, invalid operation.»

**Спросили (28:56):** «Может, она чуть-чуть медленнее будет работать? Какие-нибудь
микрооптимизации? Меньше ресурсов тратить? Или структура же будет та же самая, поэтому не будет
выигрыша? Скорее, просто для контракта.»

**Сказано (29:17):** «Сходу я не замерял перф. Это надо замерить. Я замерю и тогда напишу ответ
вместе с замером.»

**Как правильно:** [P2-03] Поправка: писать в <-chan запрещает компилятор, а не runtime.
Код канала в рантайме о направлении не знает: те же chansend1 и chanrecv1.
Обещал замер: машинный код тот же, разницы в скорости нет.
Канал можно создать и сразу однонаправленным. Подробно в репозитории курса.

Главное на практике я сказал верно: однонаправленный канал это контракт (28:41). Слово подсказали
из зала (27:28). Функция, которая получила `<-chan`, может из него только читать, и это видно прямо
в ее сигнатуре. Догадка из зала про скорость тоже верная: структура та же самая, и выигрыша нет.
Ниже замер, который я обещал.

Неверно две вещи. Первое: писать в `<-chan` запрещает не runtime, а компилятор. Программа с такой
записью просто не собирается, и до рантайма дело не доходит. Второе: канал не обязательно
создается двунаправленным. `make(chan<- int)` тоже компилируется.

## Кто запрещает писать

Давайте повторим то, что я показывал на практике, только без редактора. Возьмем функцию, которая
получает канал только для чтения, и попробуем в него записать. А заодно и закрыть его:

```go
func sendOnRecvOnly(ch <-chan int) {
	ch <- 1
}

func closeRecvOnly(ch <-chan int) {
	close(ch)
}
```

Что мы получим от `go build`? Имя файла и номер строки здесь опущены:

```
invalid operation: cannot send to receive-only channel <-chan int ch (variable of type <-chan int)
invalid operation: cannot close receive-only channel ch (variable of type <-chan int)
```

Сборка завершается с ошибкой, бинаря нет. То есть runtime здесь ничего не запрещает: программы,
которую он мог бы выполнять, просто нет.

Кто тогда проверяет? Проверка типов в компиляторе, пакет `types2`. Для отправки и приема у нее
одна функция, `chanElem`
([expr.go#L208-L213](https://github.com/golang/go/blob/go1.27.1/src/cmd/compile/internal/types2/expr.go#L208-L213)):

```go
		if recv && ch.dir == SendOnly {
			return typeErrorf("send-only channel %s", t)
		}
		if !recv && ch.dir == RecvOnly {
			return typeErrorf("receive-only channel %s", t)
		}
```

Текст ошибки собирается чуть ниже
([expr.go#L234](https://github.com/golang/go/blob/go1.27.1/src/cmd/compile/internal/types2/expr.go#L234)),
а `close` проверяется отдельно
([builtins.go#L257-L259](https://github.com/golang/go/blob/go1.27.1/src/cmd/compile/internal/types2/builtins.go#L257-L259)).
На практике ошибку показал редактор. Это та же проверка: gopls проверяет типы пакетом
`go/types`, по тем же правилам и с тем же текстом.

То же правило работает и в шаге 4. У нас в `FirstK` переменная `out` получает тип
`<-chan feed.Item` ([run.go#L19](../step4-early-exit/run.go#L19)). Поэтому закрыть `out` в
`FirstK` нельзя: `close(out)` даже не компилируется.

## Что попадает в машинный код

Хорошо, компилятор проверил. А что он генерирует? Может, для `<-chan` получается какой-то особый,
более легкий вызов? Давайте посмотрим. Возьмем четыре функции, они отличаются только типом
параметра:

```go
//go:noinline
func RecvBi(c chan int) int { return <-c }

//go:noinline
func RecvRO(c <-chan int) int { return <-c }

//go:noinline
func SendBi(c chan int, v int) { c <- v }

//go:noinline
func SendSO(c chan<- int, v int) { c <- v }
```

`go build -gcflags=-S` печатает машинный код. В обеих функциях приема стоит один и тот же вызов,
`CALL runtime.chanrecv1(SB)`. В обеих функциях отправки `CALL runtime.chansend1(SB)`. И совпадает
не только вызов. В выводе компилятора байты машинного кода в каждой паре одинаковые целиком. На
amd64 это 66 байт у приема и 62 у отправки, на arm64 по 80. Пары совпадают байт в байт на обеих
архитектурах.

Почему так? Давайте посмотрим, как компилятор строит этот вызов. Отправку `c <- v` он превращает в
вызов `chansend1` в функции `walkSend`
([expr.go#L951-L957](https://github.com/golang/go/blob/go1.27.1/src/cmd/compile/internal/walk/expr.go#L951-L957)):

```go
func walkSend(n *ir.SendStmt, init *ir.Nodes) ir.Node {
	n1 := n.Value
	n1 = typecheck.AssignConv(n1, n.Chan.Type().Elem(), "chan send")
	n1 = walkExpr(n1, init)
	n1 = typecheck.NodAddr(n1)
	return mkcall1(chanfn("chansend1", 2, n.Chan.Type()), nil, init, n.Chan, n1)
}
```

Имя функции рантайма задано прямо здесь, а `chanfn` подставляет в нее типы. От типа канала она
берет только тип элемента, `t.Elem()`
([walk.go#L137-L149](https://github.com/golang/go/blob/go1.27.1/src/cmd/compile/internal/walk/walk.go#L137-L149)).
Дальше этого места направление не передается. Получается, отправка в `chan int` и в `chan<- int`
вызывает одну и ту же функцию с одними и теми же аргументами: указатель на канал и адрес значения.
До `<-chan int` дело не доходит: такая отправка не компилируется.

С приемом так же. `v := <-c` превращается в `chanrecv1`
([assign.go#L83](https://github.com/golang/go/blob/go1.27.1/src/cmd/compile/internal/walk/assign.go#L83)),
а `v, ok := <-c` и `range` по каналу в `chanrecv2`: для `range` нужен еще и признак, что канал
закрыт
([range.go#L281-L286](https://github.com/golang/go/blob/go1.27.1/src/cmd/compile/internal/walk/range.go#L281-L286),
[assign.go#L229](https://github.com/golang/go/blob/go1.27.1/src/cmd/compile/internal/walk/assign.go#L229)).
Направление и здесь не влияет ни на выбор функции, ни на ее аргументы.

## Преобразование ничего не стоит

Откуда обычно берется `<-chan`? Из обычного канала. На практике у нас так и было: `Merge` создает
`out` как `chan feed.Item`, а возвращает `<-chan feed.Item`
([run.go#L19-L20](../step1-goroutines/run.go#L19-L20), [#L33](../step1-goroutines/run.go#L33)).
Так же устроен `feed.Source` ([feed.go#L25-L26](../feed/feed.go#L25-L26),
[#L36](../feed/feed.go#L36)). Может, хотя бы это преобразование чего-то стоит? Нет. Для
компилятора это пустое преобразование, `OCONVNOP`
([subr.go#L330-L337](https://github.com/golang/go/blob/go1.27.1/src/cmd/compile/internal/typecheck/subr.go#L330-L337)):

```go
	// 4. src is a bidirectional channel value, dst is a channel type,
	// src and dst have identical element types, and
	// either src or dst is not a named type.
	if src.IsChan() && src.ChanDir() == types.Cboth && dst.IsChan() {
		if types.Identical(src.Elem(), dst.Elem()) && (src.Sym() == nil || dst.Sym() == nil) {
			return ir.OCONVNOP, ""
		}
	}
```

Функция `func ToRO(c chan int) <-chan int { return c }` компилируется в одну инструкцию, `RET`.
То есть указатель на канал как пришел, так и уходит. И сам вызов с преобразованием,
`RecvBi(c) + RecvRO(c)` с `c chan int`, компилируется в те же байты, что `RecvBi(c) + RecvBi(c)`:
отличается только адрес вызываемой функции. Обратно, из `<-chan` в `chan`, преобразовать нельзя.
Такое правило есть только для двунаправленного канала, и проверка типов его тоже знает
([operand.go#L400-L407](https://github.com/golang/go/blob/go1.27.1/src/cmd/compile/internal/types2/operand.go#L400-L407)).

## Где тогда живет направление

В самом канале направления нет. Посмотрите на `hchan`, мы разбирали его на лекции
([chan.go#L34-L55](https://github.com/golang/go/blob/go1.27.1/src/runtime/chan.go#L34-L55)):
буфер, индексы, очереди, лок. Поля направления там нет. Поэтому у нас один и тот же канал может
быть `chan int` в одной функции и `<-chan int` в другой.

Направление есть только в типе. Во время выполнения тип канала описывает дескриптор `abi.ChanType`
([type.go#L299-L303](https://github.com/golang/go/blob/go1.27.1/src/internal/abi/type.go#L299-L303)):

```go
type ChanType struct {
	Type
	Elem *Type
	Dir  ChanDir
}
```

Кто читает `Dir`? Код канала в рантайме нет. `makechan` берет из дескриптора только тип элемента
([chan.go#L75-L76](https://github.com/golang/go/blob/go1.27.1/src/runtime/chan.go#L75-L76)), а
`chan.go` и `select.go` поле `Dir` не читают. Его читает код, который сравнивает типы во время
выполнения. Например, рантайм, когда в процессе несколько двоичных модулей (плагины или общие
библиотеки) и он сводит одинаковые типы в один ([type.go#L627](https://github.com/golang/go/blob/go1.27.1/src/runtime/type.go#L627)), или
`errors.As` через `internal/reflectlite`, если тип ошибки сам канал
([type.go#L558-L563](https://github.com/golang/go/blob/go1.27.1/src/internal/reflectlite/type.go#L558-L563)).

А проверяет направление `reflect`. `Value.Send`, `Value.Recv` (и их варианты `TrySend` и
`TryRecv`), `Value.Close` и `reflect.Select` паникуют, если направление не то: Close
([value.go#L1186-L1187](https://github.com/golang/go/blob/go1.27.1/src/reflect/value.go#L1186-L1187)),
прием ([#L2113-L2114](https://github.com/golang/go/blob/go1.27.1/src/reflect/value.go#L2113-L2114)),
отправка ([#L2146-L2147](https://github.com/golang/go/blob/go1.27.1/src/reflect/value.go#L2146-L2147)),
Select ([#L3016-L3017](https://github.com/golang/go/blob/go1.27.1/src/reflect/value.go#L3016-L3017),
[#L3047-L3048](https://github.com/golang/go/blob/go1.27.1/src/reflect/value.go#L3047-L3048)).
А `reflect.MakeChan` однонаправленный канал вообще не создает
([value.go#L3123-L3124](https://github.com/golang/go/blob/go1.27.1/src/reflect/value.go#L3123-L3124)).

То есть сказать «во время выполнения направление не проверяется» тоже было бы неточно. Точнее так:
код канала в рантайме о направлении не знает, а `reflect` его проверяет.

![Где живет направление канала: проверка типов, вызов в машинном коде, hchan и дескриптор типа](assets/p2-03-where.svg)

Что видно на картинке? Сверху запись в `<-chan int` останавливается в компиляторе. Посередине та же
запись в `chan<- int` или `chan int` доходит до одного и того же `CALL runtime.chansend1`. Снизу
единственное место, где направление остается во время выполнения: дескриптор типа. Код канала его
не читает, а `reflect` проверяет по нему направление.

## Можно ли создать канал сразу однонаправленным?

Можно. `make` принимает любой тип канала. Внутри `main`:

```go
so := make(chan<- int, 1) // только отправка
so <- 42
close(so)

ro := make(<-chan int)        // только прием
fmt.Println(len(ro), cap(ro)) // 0 0
```

Оба `make` компилируются, `go vet` молчит, программа работает. Только толку от таких каналов мало.
Из `so` никто не может читать, а в `ro` никто не может ни писать, ни закрыть его. Прием из `ro`
запаркует горутину навсегда: разбудить ее некому. Поэтому канал обычно создают двунаправленным, а
отдают однонаправленным, как в `Merge` и `feed.Source`. Этот обычный прием я и описал на практике.
Неверно было только «в любом случае».

## Замер

i5-13600KF, WSL2, 20 логических CPU, go1.27.1, 17 октября 2026. 20 раундов, в каждом все шесть
бенчмарков по одному разу, `-cpu=1`, порядок сдвигается на один каждый раунд.

Что мы ожидаем? Машинный код одинаковый, значит, и время должно быть одинаковым. Давайте все равно
замерим, как я и обещал.

Одна операция бенчмарка это 1024 отправки и 1024 приема в `make(chan int, 1024)`. В бенчмарках
приема проверяемая функция принимает, а 1024 отправки делает сам бенчмарк, одинаково во всех трех. В
бенчмарках отправки наоборот. Контроль это точная копия функции с `chan int`. Если копия
отличается от оригинала так же, как однонаправленный вариант, значит, это обычный разброс между
запусками.

| | параметр | медиана, нс на отправку и прием | диапазон, нс |
|---|---|---|---|
| прием | `chan int` | 26.6 | 26.3–27.1 |
| прием | `<-chan int` | 26.7 | 26.3–27.1 |
| прием | `chan int`, копия | 26.7 | 26.4–27.1 |
| отправка | `chan int` | 26.6 | 26.1–27.2 |
| отправка | `chan<- int` | 26.4 | 26.0–27.3 |
| отправка | `chan int`, копия | 26.5 | 25.9–26.8 |

![Шесть вариантов по 20 раундов: все точки в одной полосе, медианы от 26.4 до 26.7 нс, ось от 25.8 нс](assets/p2-03-bench.svg)

Что мы видим? Все шесть вариантов лежат в одной полосе. Внутри приема медианы расходятся меньше
чем на 1%, внутри отправки тоже. Однонаправленный канал отличается от `chan int` примерно так же,
как точная копия функции от оригинала. На отправке и `chan<- int`, и копия чуть быстрее
`chan int`, и внутри одного раунда примерно на одну и ту же величину. Получается, разницы в
скорости нет, как и предположили в зале.

## Не проверено

- Время замерено только на amd64. На arm64 сравнивался только машинный код: он тоже одинаковый.
- Замерен только буферизованный канал без ожидания, `-cpu=1`. Небуферизованный канал, прием и
  отправка с ожиданием и `select` не замерялись. Машинный код `select` с однонаправленным каналом не
  сравнивался. Для обычных приема и отправки он от буфера не зависит: это тот же код, что выше.
- Архитектуры кроме amd64 и arm64 не проверялись.
- gccgo на машине замера не установлен, его не проверяли.

Второе: какой вызов попадает в машинный код. Возьмем шаг 1:

```sh
go build -gcflags=-S ./step1-goroutines 2>&1 | grep -E '[[:space:]]CALL[[:space:]]+runtime\.chan'
```

```
	0x006c 00108 (…/step1-goroutines/run.go:25)	CALL	runtime.chansend1(SB)
	0x0080 00128 (…/step1-goroutines/run.go:24)	CALL	runtime.chanrecv2(SB)
```

Это amd64. На arm64, например на Mac с Apple Silicon, смещения другие, а вызовы те же. Вместо `…`
будет путь к вашей папке.

Строка 24 это `for it := range in`, а `in` здесь `<-chan feed.Item`. Строка 25 это `out <- it`,
и `out` обычный `chan feed.Item`. Почему мы видим `chanrecv2`, а не `chanrecv1` из плашки? Для
`range` нужен признак, что канал закрыт, и `chanrecv2` его возвращает. Это та же функция, что
`v, ok := <-ch`, и для `chan`, и для `<-chan`.
