# L2-08. Кто будит select: CAS по g.selectDone, а не планировщик

Этот разбор закрывает плашку L2-08, в видео она стоит дважды. На лекции после вопроса из зала я
обещал более подробный разбор (36:27). Вот он.

**Спросили (33:52):** «Не может быть такого, что несколько sudog одновременно разбудят горутину?
Выглядит страшно. Или это невозможно, чтобы они попытались одновременно?»

**Сказано (34:19):** «У нас по сути только одна горутина, но для этой одной горутины у нас много
структур sudog. Можем ли мы несколько горутин разбудить, поставить в runnext? Нет, не можем. Она
только одна.»

**Как правильно:** [L2-08] Поправка: один case будит select не из-за планировщика. Будить могут несколько
каналов сразу. Выигрывает тот, чей CAS по g.selectDone прошел (chan.go:897), остальные
берут следующего ждущего. Подробно в репозитории курса.

**Сказано (41:44 и 44:52):** «Ждем, пока нашу горутину кто-то разбудит. Разбудить ее
гарантированно может только один case. Как мы помним из первой лекции, гонок в шедулировании
горутин для запуска у нас нет.» И дальше: «Мы здесь используем свойства планировщика, а не
какой-то определенный лок. На все мы берем лок, а используем свойства планировщика.»

**Как правильно:** [L2-08] Поправка: не «гонок в планировщике нет», а CAS по g.selectDone.
Подробно в репозитории курса.

На лекции я верно сказал главное: select просыпается один раз и возвращает ровно один case. Верно
и то, что горутина у select одна и дважды разбудить ее нельзя. Вопрос из зала тоже был верный.
Несколько каналов действительно пытаются разбудить select одновременно. Неверно другое: что гонки
нет и что ее снимает планировщик. Гонка есть, и решает ее один CAS по полю горутины.

## Что select делает перед сном

Давайте вспомним проход 2. Для каждого case select кладет свой sudog в очередь канала. Если case
принимает, sudog встает в `recvq`, если отправляет, в `sendq`
([`select.go:309–342`](https://github.com/golang/go/blob/go1.27.1/src/runtime/select.go#L309-L342)).
Все это идет под локами всех каналов. Потом `gopark`, и перед самым сном `selparkcommit` отпускает
все локи ([`select.go:84–99`](https://github.com/golang/go/blob/go1.27.1/src/runtime/select.go#L84-L99)).

Что у нас получается? Горутина спит, и ни одного лока у нее нет. Ее sudog лежат в N очередях, и
каждую очередь охраняет свой `c.lock`.

## Два канала, два лока

Пусть теперь в канал a и в канал b отправляют одновременно, с двух разных P. Отправитель в a берет
лок a ([`chan.go:222`](https://github.com/golang/go/blob/go1.27.1/src/runtime/chan.go#L222)),
отправитель в b берет лок b. Друг друга они не ждут, это разные локи. Каждый смотрит в `recvq`
своего канала и находит там наш sudog
([`chan.go:229`](https://github.com/golang/go/blob/go1.27.1/src/runtime/chan.go#L229)).

То есть до одной спящей горутины одновременно добрались два отправителя. Кто ее разбудит? Ответ в
`waitq.dequeue` ([`chan.go:893–901`](https://github.com/golang/go/blob/go1.27.1/src/runtime/chan.go#L893-L901)):

```go
		// We use a flag in the G struct to tell us when someone
		// else has won the race to signal this goroutine but the goroutine
		// hasn't removed itself from the queue yet.
		if sgp.isSelect {
			if !sgp.g.selectDone.CompareAndSwap(0, 1) {
				// We lost the race to wake this goroutine.
				continue
			}
		}
```

Сначала `dequeue` снимает первый sudog своей очереди
([`chan.go:874–886`](https://github.com/golang/go/blob/go1.27.1/src/runtime/chan.go#L874-L886)).
Потом, если это sudog от select, делает CAS по полю горутины `g.selectDone`, из 0 в 1. CAS
атомарный, поэтому из 0 в 1 поле переведет только один отправитель. Он и выиграл: отдает значение
и будит горутину ([`chan.go:343–350`](https://github.com/golang/go/blob/go1.27.1/src/runtime/chan.go#L343-L350)).

Комментарий над этим кодом прямо называет окно гонки. Оно длится от пробуждения через другой
case до момента, когда горутина снова возьмет локи каналов
([`chan.go:888–895`](https://github.com/golang/go/blob/go1.27.1/src/runtime/chan.go#L888-L895)).
Поле так и описано: «are we participating in a select and did someone win the race?»
([`runtime2.go:566`](https://github.com/golang/go/blob/go1.27.1/src/runtime/runtime2.go#L566)).

## Что делает проигравший

А второй отправитель? Его CAS не прошел, в поле уже 1. Наш sudog он к этому моменту уже снял со
своей очереди. `continue` возвращает его в начало цикла, и он берет следующую горутину из той же
очереди. Если там кто-то есть, отправитель работает уже с ним. Если никого нет, `dequeue` вернет
nil. Тогда отправитель ведет себя так, будто получателя не было: кладет значение в буфер или сам
паркуется в `sendq` своего канала. Значение не теряется, его заберет следующий прием из этого
канала.

## Что select делает после пробуждения

Горутина просыпается и сразу снова берет все локи
([`select.go:354–358`](https://github.com/golang/go/blob/go1.27.1/src/runtime/select.go#L354-L358)):

```go
	sellock(scases, lockorder)

	gp.selectDone.Store(0)
	sg = (*sudog)(gp.param)
	gp.param = nil
```

`selectDone` снова 0, для следующего select. В `gp.param` лежит sudog победителя, по нему select
узнает, какой case сработал. Дальше проход 3 убирает остальные sudog из очередей
([`select.go:360–401`](https://github.com/golang/go/blob/go1.27.1/src/runtime/select.go#L360-L401)).
Из очереди проигравшего наш sudog уже снят. `dequeueSudoG` это видит и ничего не делает
([`select.go:653–658`](https://github.com/golang/go/blob/go1.27.1/src/runtime/select.go#L653-L658)).
Получается, проход 3 и проигравший друг другу не мешают.

## Проверим: бывает ли гонка на самом деле

Код говорит, что гонка возможна. А как часто она бывает? Давайте посмотрим.

Программа [`l2-08-probe`](l2-08-probe/main.go): одна горутина спит в select на 16 каналах. Потом
16 других горутин в один момент отправляют, каждая в свой канал. Чтобы считать проигравших, в копию
`runtime/chan.go` добавлены два счетчика рядом с CAS ([`count.diff`](l2-08-probe/count.diff)).
Больше в рантайме ничего не меняется.

Что мы видим? На 20 CPU гонка была почти при каждом пробуждении, в 99.9% случаев. Из 15 других
отправителей проигрывали почти все, в среднем 14.98. На 8 и 4 CPU гонок чуть меньше, 86–92%. Так же
ведет себя select, который отправляет: тогда его будят 16 получателей.

Почему проигрывают почти все? Победитель кладет нашу горутину в runnext своего P, а сам работает
дальше. Пока горутина ждет CPU, окно открыто, и остальные отправители успевают дойти до CAS. Если
победитель сразу отдает P (`runtime.Gosched`), проигравших меньше, в среднем 9 из 15. Но гонка все
равно почти при каждом пробуждении.

При этом каждый select вернул ровно один case, и каждое значение дошло ровно один раз.

## А если убрать CAS?

Теперь главная проверка. Если одно пробуждение обеспечивает планировщик, то без CAS ничего не изменится.
Давайте уберем проверку из `dequeue`: пусть выигрывает каждый ([`nocas.diff`](l2-08-probe/nocas.diff)).

Рантайм падает:

```
fatal error: bad g->status in ready
```

Так закончился каждый из 66 запусков: на 20 CPU, на 4 и на одном P. Почему? Второй «победитель»
тоже вызывает `goready`, а горутина уже не спит. Планировщик это проверяет
([`proc.go:1138–1141`](https://github.com/golang/go/blob/go1.27.1/src/runtime/proc.go#L1138-L1141)):

```go
	if status&^_Gscan != _Gwaiting {
		dumpgstatus(gp)
		throw("bad g->status in ready")
	}
```

То есть планировщик не делает пробуждение единственным. Он требует, чтобы оно было одно, и падает,
если это не так. Единственным его делает CAS.

## А на одном P?

Может быть, на одном P гонки нет? Там отправители и правда идут по очереди. Победитель кладет select
в runnext, и select обычно запускается раньше следующего отправителя. Здесь то, что я сказал на
лекции, почти верно.

Почти. С `GOMAXPROCS=1` CAS проигрывали в 2% пробуждений. Откуда? Как мы помним из первой лекции,
каждый 61-й раз, выбирая следующую горутину, P сначала смотрит в глобальную очередь
([`proc.go:3455–3458`](https://github.com/golang/go/blob/go1.27.1/src/runtime/proc.go#L3455-L3458)):

```go
	// Check the global runnable queue once in a while to ensure fairness.
	// Otherwise two goroutines can completely occupy the local runqueue
	// by constantly respawning each other.
	if pp.schedtick%61 == 0 && !sched.runq.empty() {
```

На одном P отправители ждут старта в цикле с `runtime.Gosched`, поэтому сидят в глобальной
очереди. Раз в 61 выбор один из них запускается раньше select и проигрывает CAS. Проверка: если в копии
рантайма отключить только эту строку, проигравших на одном P ноль, во всех прогонах. А без CAS программа
на одном P падает так же, как на 20.

Получается, порядок не гарантирован даже на одном P. Гарантию дает CAS, на любом числе P.

## Что это значит для Broadcaster

В домашке Broadcaster (T-02) такой select появляется, когда одна горутина ждет сразу на нескольких
каналах. Например, `Publish` ждет в select на каналах подписчиков, а подписчики читают
одновременно. Это в точности замер с `-dir=send`. Будят 16 получателей, выигрывает один.

Что здесь гарантирует рантайм? Select вернет ровно один case. Каждое значение дойдет ровно один
раз. Проигравший ничего не теряет: он ждет в очереди своего канала, будто select там и не было.
Свой мьютекс вокруг select для этого не нужен, CAS уже есть в рантайме. А чего рантайм не гарантирует? Какой
case выиграет. Это решает гонка, а не ваш код, поэтому полагаться на порядок нельзя.

## Замер

i5-13600KF, WSL2, 20 логических CPU, go1.27.1, 16 октября 2026. 16 каналов, все отправители
стартуют вместе, select к этому моменту спит:

| условие | прогонов × пробуждений | пробуждений с проигравшим CAS | проигравших на пробуждение, из 15 |
|---|---|---|---|
| select принимает, 20 CPU | 5 × 20 000, медиана | 99.9% | 14.98 |
| select отправляет, 20 CPU | 5 × 20 000, медиана | 99.9% | 14.97 |
| select принимает, победитель сразу отдает P | 1 × 20 000 | 98.6% | 9.35 |
| `taskset -c 0-7` | 1 × 20 000 | 92.3% | 6.15 |
| `taskset -c 0-3` | 1 × 5000 | 86.1% | 5.27 |
| `GOMAXPROCS=1` | 3 × 5000 | 2.0% | 0.02 |
| `GOMAXPROCS=1`, без проверки `schedtick%61` | 3 × 5000 | 0 | 0 |

С 2, 4 и 8 отправителями на 20 CPU проигравших в среднем 1.00, 2.99 и 6.99, то есть тоже почти все
остальные. Рантайм без правок прошел по 20 000 пробуждений с select, который принимает, и с select,
который отправляет. Каждый select вернул один case, каждое значение дошло один раз.

Без CAS:

| условие | пробуждений в запуске | запусков упало |
|---|---|---|
| 20 CPU, select принимает | 1000 | 20 из 20 |
| 20 CPU, select отправляет | 1000 | 20 из 20 |
| `taskset -c 0-3` | 1000 | 10 из 10 |
| `GOMAXPROCS=1` | 5000 | 16 из 16 |

Запуск всего с одним пробуждением падает не всегда (11 из 20 и 18 из 20). В первом раунде не
все отправители успевают попасть в окно гонки.

## Не проверено

- Как часто это бывает в настоящей программе. Замер берет худший случай: все будят в один момент, и
  select точно спит. Сколько отправителей проигрывает за одно пробуждение, зависит от того, как
  быстро разбуженная горутина снова получит CPU (14.98 против 9.35 выше).
- Случай, когда проигравший находит в очереди еще одну горутину. В замере за нашим sudog никого нет,
  и проигравший паркуется сам. Этот случай видно только в коде: `continue` возвращает в начало цикла
  ([`chan.go:873–874`](https://github.com/golang/go/blob/go1.27.1/src/runtime/chan.go#L873-L874)).

## Проверить самому

Из папки [`l2-08-probe`](l2-08-probe/):

```sh
go run . -n=16
```

Это обычный рантайм. Счетчиков в нем нет, но программа проверяет, что каждый select вернул один
case и каждое значение дошло один раз (`bad=0`).

Теперь со счетчиками. Как и в [L2-11](L2-11.md), `go -overlay` не подменяет файлы в кэше модулей,
поэтому нужна копия GOROOT.

```sh
cp -R "$(go env GOROOT)" /tmp/goroot && chmod -R u+w /tmp/goroot
cp /tmp/goroot/src/runtime/chan.go /tmp/chan-count.go && patch /tmp/chan-count.go count.diff
cp /tmp/goroot/src/runtime/chan.go /tmp/chan-nocas.go && patch /tmp/chan-nocas.go nocas.diff
echo '{"Replace":{"/tmp/goroot/src/runtime/chan.go":"/tmp/chan-count.go"}}' > /tmp/count.json
echo '{"Replace":{"/tmp/goroot/src/runtime/chan.go":"/tmp/chan-nocas.go"}}' > /tmp/nocas.json

GOTOOLCHAIN=local /tmp/goroot/bin/go run -tags l208count -overlay=/tmp/count.json . -n=16
GOTOOLCHAIN=local /tmp/goroot/bin/go run -tags l208count -overlay=/tmp/count.json . -n=16 -dir=send
GOMAXPROCS=1 GOTOOLCHAIN=local /tmp/goroot/bin/go run -tags l208count -overlay=/tmp/count.json . -rounds=5000
GOTOOLCHAIN=local /tmp/goroot/bin/go run -tags l208count -overlay=/tmp/nocas.json . -rounds=1000
```

Смотрите на `rounds_with_loss` и `lost_per_parked`. Последняя команда должна упасть с
`fatal error: bad g->status in ready`. На 8 и 4 CPU гонка будет примерно в 92% и 86% пробуждений, на одном P
в 2%. Если CPU меньше 18, отправители ждут старта в цикле с `runtime.Gosched`, программа включает
это сама (`yield=true`).
