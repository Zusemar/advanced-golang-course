# P2-05. Горутина на вход или один select: горутины быстрее при любом числе входов

**Спросили (48:16):** «Зависит ли это от инпута?»

**Сказано (48:16–49:10):** «Хороший вопрос. У нас select nil сделан так, что мы только два входа
там можем принимать, произвольно не можем. Я еще сделаю бенчмарк, что было бы, если бы у нас было
больше входящих каналов: остался бы быстрее вариант с горутинами, или вариант select с занилением
в какой-то момент смог бы стать быстрее.»

**Как правильно:** [P2-05] Обещал замер: горутины быстрее при любом числе входов, кривые не пересекаются.
При 2 входах select медленнее на 2–12%, при 16 в 2.3–2.5 раза, при 128 в 16–17 раз.
select на каждый элемент сортирует и лочит все N каналов. Подробно в репозитории курса.

На практике я сказал верно: select из шага 3 принимает ровно два входа. Case в select задаются
при компиляции, поэтому для N входов его надо написать заново. Здесь такой select сгенерирован
для N от 2 до 128, код лежит в [`p2-05-probe`](p2-05-probe/). Ответ на вопрос такой: select
горутины не догоняет. Горутины быстрее при любом N, и чем больше входов, тем больше разрыв.

## Что сравниваем

Давайте сначала посмотрим на два варианта. Шаг 1 это `Merge(ins ...)`: на каждый вход своя
горутина, она пересылает элементы в общий `out`. Входов может быть сколько угодно.

Второй вариант это шаг 3, расширенный до N case. Вот он для четырех входов (`sel4.go`):

```go
for open := 4; open > 0; {
	select {
	case it, ok := <-c0:
		if !ok {
			c0 = nil
			open--
			continue
		}
		out <- it
	// case <-c1, <-c2 и <-c3 устроены так же
```

Закрытый вход выключается через nil, как в шаге 3. Для 8, 16, 32, 64 и 128 входов то же самое,
только case больше. Этот код пишет генератор `gen.go`.

Условия как в бенчмарке практики: каналы небуферизованные, sleep нет. Всего 400 тысяч элементов
на запуск, при любом N, поровну на каждый вход. Один прогрев, пять замеров и медиана из них.

## Прикинем

Давайте прикинем, что будет с ростом N. В шаге 1 элемент проходит так: горутина входа принимает
его из своего канала и отправляет в `out`. Две операции, и каждая на одном канале. Число входов
сюда не входит.

В select на каждый элемент приходится один `select` по всем N case. Как мы увидим дальше, до
готового case он работает со всеми N каналами. Получается, ожидаем такое: шаг 1 от N почти не
зависит, а select с ростом N дорожает.

## Что показал замер

![Нс на элемент при N входах, -cpu 1, 2 и 8](assets/p2-05-sweep.svg)

Мы видим, что так и есть. На одном CPU шаг 1 при 128 входах почти такой же, как при двух: разница
меньше 4%. А select при двух входах медленнее совсем немного, при 16 уже в 2.3 раза, при 128
в 17 раз. На 2 и 8 CPU картина та же. Кривые нигде не пересекаются.

Может, что-то меняется, когда входов больше, чем P? На 1 CPU их больше всегда, на 8 CPU с 16
входов. А CPU на этой машине 20, то есть с 32 входов их меньше, чем входов. Излома нет ни там,
ни там: кривая шага 1 растет плавно.

## Почему select дорожает

Давайте посмотрим, что делает `select`, прежде чем забрать элемент. Как мы помним из
[L2-11](../../lecture/corrections/L2-11.md), до прохода 1 у него три шага. Он перемешивает все
case ([`select.go:191–194`](https://github.com/golang/go/blob/go1.27.1/src/runtime/select.go#L191-L194)).
Дальше сортирует их по адресу канала, это heapsort
([`select.go:206–212`](https://github.com/golang/go/blob/go1.27.1/src/runtime/select.go#L206-L212)):

```go
	// sort the cases by Hchan address to get the locking order.
	// simple heap sort, to guarantee n log n time and constant stack footprint.
	for i := range lockorder {
		j := i
		// Start with the pollorder to permute cases on the same channel.
		c := scases[pollorder[i]].c
		for j > 0 && scases[lockorder[(j-1)/2]].c.sortkey() < c.sortkey() {
```

Потом берет лок каждого канала
([`select.go:34–43`](https://github.com/golang/go/blob/go1.27.1/src/runtime/select.go#L34-L43)):

```go
func sellock(scases []scase, lockorder []uint16) {
	var c *hchan
	for _, o := range lockorder {
		c0 := scases[o].c
		if c0 != c {
			c = c0
			lock(&c.lock)
		}
	}
}
```

У нас все N каналов разные, значит N локов. В конце `select` так же отпускает все N.

А дальше проход 1 ищет готовый case
([`select.go:275–279`](https://github.com/golang/go/blob/go1.27.1/src/runtime/select.go#L275-L279)):

```go
		if casi >= nsends {
			sg = c.sendq.dequeue()
			if sg != nil {
				goto recv
			}
```

Находит он его почти всегда сразу. Источники быстрее merge, и каждый уже ждет на отправке в
своем канале. По трейсу так у 97–100% элементов. То есть `select` почти не паркуется, и
проходов 2 и 3 почти нет. Получается, на каждый элемент `select` платит за все N каналов, а
забирает из одного.

На практике это предположили (51:52): «Чем больше каналов, тем больше будет расти? Потому что
сортировка n log n». Так и есть: каждый следующий канал стоит дороже предыдущего. Как время
делится между сортировкой и локами, разобрано в L2-11. У 16 разных каналов больше половины уходит
на сортировку адресов, около трети на lock/unlock.

## select без горутин

Может, дорожает не `select`, а планирование? Все-таки N источников, N каналов. Это проверяется
отдельно. Возьмем одну горутину и N буферизованных каналов, в каждом лежит по элементу. Тот же
`select` по N case забирает элемент и кладет его обратно. Других горутин нет, будить некого.

![Рост select в merge и одного select без горутин](assets/p2-05-control.svg)

Мы видим, что рост почти совпадает. От 2 до 128 каналов merge на select дорожает почти на столько же,
сколько один `select` без горутин. То есть весь рост это сам `select`. И планирование у нас от N
не зависит. По трейсу на элемент приходится два запуска горутин, в обоих вариантах и при любом N.

## А горутины совсем бесплатны?

Не совсем. Мы видим, что на 2 и 8 CPU шаг 1 с ростом N немного дорожает: при 128 входах в 1.3–1.5
раза. И тратит больше CPU: на 8 CPU при 128 входах CPU в 2.6 раза больше wall. Горутины входов работают
параллельно, но быстрее от этого не становится. Все элементы все равно проходят через один `out`
и одного читателя. Но select тратит CPU еще больше: при двух входах примерно столько же, а при
128 входах в 8–10 раз больше.

## Свободный P тоже стоит времени

На 2 и 8 CPU `select` теряет еще и на другом. При 64 входах он примерно в 1.6–1.7 раза медленнее,
чем на одном CPU. Откуда это? Давайте посмотрим, что происходит после прохода 1.

Когда проход 1 забирает элемент у источника, он будит этот источник. Runtime кладет его в очередь
нашего P и вызывает `wakep`
([`proc.go:1150–1151`](https://github.com/golang/go/blob/go1.27.1/src/runtime/proc.go#L1150-L1151)):

```go
	runqput(mp.p.ptr(), gp, next)
	wakep()
```

Если есть свободный P, `wakep` будит под него поток. Этот P забирает себе разбуженные источники.
По трейсу при 64 входах на двух CPU источник переходит на другой P примерно у каждого четвертого
элемента.

Проверка: второй P занимает горутина, которая просто крутит цикл. Свободного P больше нет, и потеря
пропадает целиком: `select` снова работает как на одном CPU. То же самое, если оба P посадить на
один CPU (`taskset -c 0`).

## Если N известно только во время работы

В реальном коде число входов часто заранее неизвестно: подписчики, соединения, шарды. `select` на
N case тогда не написать. Для этого есть `reflect.Select`, он принимает срез case.

Но он еще медленнее. При двух входах на четверть-треть медленнее горутин, при 128 в 25–32 раза.
Почему? На каждом вызове `reflect.Select` заново проверяет каждый case, в том числе направление
канала. И под каждый case выделяет память для принятого значения
([`value.go:3044–3052`](https://github.com/golang/go/blob/go1.27.1/src/reflect/value.go#L3044-L3052)):

```go
			ch.mustBe(Chan)
			ch.mustBeExported()
			tt := (*chanType)(unsafe.Pointer(ch.typ()))
			if ChanDir(tt.Dir)&RecvDir == 0 {
				panic("reflect.Select: RecvDir case using send-only channel")
			}
			rc.ch = ch.pointer()
			rc.typ = toRType(&tt.Type)
			rc.val = unsafe_New(tt.Elem)
```

Дальше runtime еще собирает из них массивы case
([`select.go:573–574`](https://github.com/golang/go/blob/go1.27.1/src/runtime/select.go#L573-L574))
и вызывает тот же `selectgo`. По `-benchmem` это два выделения памяти на элемент при двух входах
и около двадцати при 16. Получается, когда N известно только во время работы, горутина на вход и
проще, и быстрее.

## Не проверено

- Что именно стоит времени, когда второй P свободен: поток, который ищет работу (spinning), его
  пробуждение или отправка украденного источника с другого ядра. По отдельности это не
  взвешивалось. Непонятно и то, почему потеря больше всего при 64 входах, а при 128 меньше. И
  почему с двумя P на двух закрепленных CPU при 16 входах она пропадает, а при 64 остается в 1.5
  раза.
- Как рост select делится между сортировкой и локами на этой нагрузке. Здесь части не удалялись,
  есть только разбор L2-11 для 16 каналов.
- Машины меньше чем с 4 CPU. Под `taskset -c 0-3` картина та же, меньше не проверялось.
